# 이메일 인증과 계정별 기록 보관

[운영 앱](https://eru-ai-investment-simulator.vercel.app)은 처음부터 이메일 인증이 필요합니다. Supabase Auth가 인증하고 Resend SMTP가 인증메일을 발송합니다. 비밀번호 입력과 별도의 가입 화면은 없습니다.

## 사용자 흐름

1. 이메일 입력 → 인증번호 받기 → 최신 메일의 번호 입력 → 내 투자 기록.
2. 새 투자 시작 → 성향·코인·비율 설정 → 사용자 최종 승인 → 다음 일봉 시가 체결.
3. 내 투자 기록에서 작성 중인 계획, 진행 중인 투자, 완료한 투자 복기를 다시 엽니다.
4. 기록 목록으로 나가기·새 게임 시작·로그아웃은 기존 실행을 일시정지합니다. 체결을 취소하거나 기록을 삭제하지 않습니다.
5. 같은 이메일로 다른 기기에서 로그인해 작성 중인 계획과 과거 게임을 확인할 수 있습니다. 준비·정지·종료 상태에는 주기적으로 게임을 조회하지 않습니다.

첫 인증 후 시작한 모든 게임이 계정에 자동 연결됩니다. 초기 구성·매매·판단·AI 대화·복기를 게임 단위로 보관하며, 포트폴리오 초안도 변경 후 저장합니다. 초안은 주문이 아니며 저장만으로 자산·시계·잔고가 바뀌지 않습니다. 입력은 묶어서 저장하고, 투자 시작·화면 나가기 전에 대기 중인 저장을 완료합니다. 실패 상태는 화면에 표시합니다.

## 인증과 소유권

- `POST /api/auth/send-code`는 Supabase Auth `/otp`, `POST /api/auth/verify`는 `/verify`를 사용합니다. 실제 인증번호 생성·유효기간·검증은 Supabase가 담당합니다.
- 인증 토큰과 갱신 토큰은 `HttpOnly`, 운영 `Secure`, `SameSite=Lax` 쿠키에 둡니다. 토큰을 JSON 응답·URL·localStorage에 보내지 않습니다. 브라우저에는 사용자 ID와 본인 이메일만 반환합니다.
- 매 API 요청에서 Supabase `/user`로 확인한 사용자만 신뢰합니다. 만료 시간을 넘기지 않는 최대 30초의 제한된 신원 캐시를 사용하며, 이메일 확인이 없는 사용자와 익명 계정은 거부합니다. 토큰의 서명 없는 내용만으로 인증하지 않습니다.
- 만료 시 갱신 토큰으로 회전하고, 실패하면 이메일 인증으로 돌아갑니다. 교차 사이트의 Origin 요청은 거부합니다.
- 모든 게임 생성·조회·시작·주문·상담·복기·초안 저장은 인증을 요구합니다. 서버가 생성 시 실제 사용자 ID를 `state.owner_id`에 저장하며 클라이언트의 소유자 입력을 받지 않습니다.
- 조회와 변경 모두 소유자를 **게임 시계 진행 전에** 확인합니다. 다른 계정이나 비회원 원본 게임에는 404를 반환하며 게임의 존재·장부·시간을 변경하지 않습니다.
- 계정 목록은 환경과 소유자로 제한해 읽고, 반환 전에도 소유자를 확인합니다. 응답에는 상태·게임 날짜·최근 저장 자산·진행률·체결 수·초기 비중만 포함하며 시세 원본·식별자·미래 사건·대화 원문은 포함하지 않습니다.
- Supabase 데이터 테이블은 기존대로 서버 전용입니다. anon/authenticated 직접 읽기 권한을 열지 않습니다. 별도 테이블 초기화나 데이터 삭제 없이 세션 JSON의 소유자 메타데이터와 기존 revision CAS를 사용합니다.

비회원 과거 기록은 서버에 보존하되 로그인한 이메일만으로 원래 소유자를 확인할 수 없어 자동 연결하지 않습니다. 브라우저의 예전 게임 ID만 제시해 다른 계정으로 가져오는 기능도 제공하지 않습니다.

## Resend 설정

사용자가 Supabase의 Custom SMTP와 인증번호 메일 템플릿을 등록했습니다. 앱은 기존 서버 `SUPABASE_URL`, `SUPABASE_SECRET_KEY`를 사용하며 Resend 키를 Vercel이나 브라우저에 추가하지 않습니다.

| Supabase SMTP 항목 | 설정 |
|---|---|
| Sender email | Resend에서 검증한 발신 도메인 주소 |
| Sender name | ERU AI |
| Host | smtp.resend.com |
| Port | 465 |
| Username | resend |
| Password | Resend API 키 · Supabase 설정에서만 입력 |

Confirm signup과 Magic Link 메일에 `{{ .Token }}`을 포함합니다. 기본 Supabase SMTP는 조직 팀원 주소와 발송량 제한이 있어 일반 사용자용 Resend SMTP 설정이 필요합니다. 발송 도메인 인증과 발송 권한을 가진 키를 사용합니다.

- [Resend SMTP 공식 문서](https://resend.com/docs/send-with-smtp)
- [Supabase 인증번호 로그인](https://supabase.com/docs/guides/auth/auth-email-passwordless)
- [Supabase 메일 템플릿](https://supabase.com/docs/guides/auth/auth-email-templates)

## 검증

`tests/test_account_auth.py`는 메일 공급자의 HTTP만 대체하고 실제 인증·소유권 경계를 그대로 검증합니다. 인증 전 모든 게임 API 차단, 위조·미인증 사용자 거부, 쿠키 속성, 만료 갱신, 로그아웃·정지·주문 보존, 소유자 강제 입력 거부, 비회원 보존, 다른 계정의 읽기·주문·복기·초안 거부와 시계 불변, Supabase CAS 상태를 확인합니다.

`scripts/account_smoke.cjs`는 별도의 로컬 QA 공급자와 매번 새 SQLite 파일로 화면을 확인합니다. 실제 검증 시세를 사용하며, 테스트 공급자·키·인증번호는 운영 코드 경로에서 사용하지 않습니다. QA 서버 파일과 DB·화면·세션은 무시된 `test-results/`와 로컬 캐시에만 두고 테스트 파일은 배포에서도 제외합니다.

현행 검증: 백엔드 173개, archive unittest 10개, 프론트엔드 타입 검사·테스트 16개·빌드. 브라우저는 로그인 전 게임 생성 0건, HttpOnly 쿠키, 두 계정 격리, 별도 브라우저 초안 복원, 초기 승인·체결·정지·이어하기·복기, 새로고침·로그아웃·320/390px를 확인합니다. 실제 Resend 수신과 사용자 인증번호 입력은 운영 배포 후 사용자의 메일함에서 확인합니다.
